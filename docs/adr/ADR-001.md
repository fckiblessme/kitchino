# ADR-001. Стек и модель исполнения

| Поле | Значение |
|---|---|
| Статус | Принято |
| Дата | 10.10.2026 |
| Автор | команда проекта Kitchino: Скрыпникова Д.М., Стрельцова В.С., Чемякина П.Д. |
| Характер записи | Ретроспективная: оформлена по факту работающего решения |

## Контекст

Продукт – приложение для персонала ресторана: учет склада и рецептов, контроль срока годности готовых блюд с подсказкой «скидка или списание», фиксация, кто приготовил блюдо, роли сотрудников и журнал критичных действий.

Ограничения, которые определили выбор:

- командный учебный проект на трех человек, срок – один семестр, разработка идет параллельно с другими дисциплинами;
- сотрудник работает на одном устройстве; сервер и синхронизация между устройствами не требуются;
- доступ к сети не нужен: все данные локальные, что упрощает модель угроз и снимает зависимость от внешних сервисов;
- по требованиям курса у продукта должно быть собственное содержательное ядро – правила и алгоритмы команды, – а внешним ресурсом выступает база данных;
- проверки логики должны быть воспроизводимы без эмулятора и без ручной подготовки среды.

## Решение

Принят следующий стек:

- **Kotlin** – язык разработки;
- **Jetpack Compose** – интерфейс;
- **Room** поверх SQLite – локальное хранилище как основной внешний ресурс продукта;
- **корутины и Flow** – асинхронная работа с базой и передача изменений в интерфейс;
- сборка – **Gradle** и **Android Gradle Plugin**, версии зависимостей зафиксированы в `gradle/libs.versions.toml`.

Параметры сборки: `minSdk 24`, `targetSdk 36`, `compileSdk 37`. Разрешение `INTERNET` в манифест не добавлено, сетевого кода в проекте нет.

## Модель исполнения

- приложение исполняется на платформе Android в управляемой среде (ART) в одном процессе;
- главный поток занят только интерфейсом; обращения к базе выполняются `suspend`-функциями из `viewModelScope`, а изменения возвращаются в интерфейс потоком `Flow`;
- правила и расчеты вынесены в **чистые функции** без обращений к системе: например, движок решения по сроку годности получает текущее время параметром, а не читает системные часы;
- следствие: логику можно проверять модульными тестами на JVM – без эмулятора, без базы и без подмены зависимостей;
- сохраняемые данные лежат в базе Room; схема данных версионируется, при изменении версии пишется миграция.

## Рассмотренные альтернативы

Систематическое сравнение вариантов на старте не проводилось: стек выбран командой по требованиям темы и согласован с преподавателем. Осознанно отклонено:

- **сетевое приложение с сервером** – требует инфраструктуры, доступа к сети и отдельной модели угроз, но ничего не добавляет основному сценарию;
- **хранение данных в файлах вместо базы** – потребовало бы своей реализации запросов, транзакций и версионирования схемы, то есть повторения того, что уже дает Room;
- **XML-разметка интерфейса** – выбран Compose как более компактный способ описывать экраны на том же языке, что и логика.

## Последствия

Что решение дает:

- один язык для интерфейса, логики и данных, без переключения между технологиями;
- Room дает транзакции и реактивные запросы: интерфейс обновляется сам при изменении данных в базе;
- чистые функции с параметром времени делают ядро тестируемым без эмулятора;
- отсутствие сети упрощает модель угроз и делает проверки воспроизводимыми.

Чем за это платим:

- привязка к платформе Android: код не переносится на другие платформы без переработки;
- Room требует версионирования схемы: при изменении сущностей нужно поднимать версию и писать миграцию, иначе приложение падает при обновлении у уже установленной версии. Это уже наблюдалось на практике: база, созданная прежней сборкой, не открывалась новым кодом;
- Compose и корутины требуют освоения, что влияет на скорость первых недель;
- синхронизации между устройствами нет – это осознанное ограничение MVP, а не недосмотр.

## Условие пересмотра

Запись пересматривается, если:

- появится требование синхронизации между устройствами или серверной части: понадобится сетевой слой, аутентификация и модель разрешения конфликтов;
- потребуется поддержка другой платформы;
- объем данных или нагрузка выйдут за пределы, при которых локальная база на устройстве остается достаточной.
