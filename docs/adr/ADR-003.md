# ADR-003. Выделение контракта WarehouseApi с двумя реализациями

| Поле | Значение |
|---|---|
| Статус | Принято |
| Дата | 19.10.2026 |
| Автор | Скрыпникова Д.М. |
| Характер записи | Ретроспективная: оформлена по факту работающего решения |

## Контекст

Модуль склада и рецептов отвечает за списание ингредиентов по рецепту (FR-01, FR-02, FR-03, FR-06). Потребитель — экран «Приготовить блюдо» через `MakeDishViewModel`. Изначально потребитель зависел от конкретного класса `ConsumeIngredientsUseCase`, что не позволяло проверить поведение потребителя без запущенной базы Room и эмулятора.

Для практической работы №2 требовалось: потребитель зависит от контракта, реализацию можно подменить без изменения потребителя, обе реализации проверяются.

## Рассмотренные варианты

**Вариант 1. Потребитель зависит от `ConsumeIngredientsUseCase` напрямую.**

Плюсы: меньше файлов, проще для MVP.
Минусы: потребитель связан с конкретной реализацией и базой Room; проверить логику обработки результата (`Success`, `InsufficientStock`, `RecipeNotFound`) без базы нельзя; подмена требует переписывания потребителя.

**Вариант 2. Выделить контракт `WarehouseApi`, потребитель зависит от контракта, реализация передается через точку сборки.**

Плюсы: потребитель не знает о базе; вторая реализация (`FakeWarehouseApi`) работает в памяти; тесты потребителя запускаются на JVM без эмулятора; подмена — замена аргумента в фабрике.
Минусы: дополнительный интерфейс и класс `FakeWarehouseApi`; нужно поддерживать одинаковый контракт в обеих реализациях.

**Вариант 3. Подменять не реализацию контракта, а репозиторий под потребителем.**

Плюсы: репозиторий уже есть, меньше новых сущностей.
Минусы: потребитель все равно зависит от конкретного use case; подмена репозитория не убирает зависимость от `ConsumeIngredientsUseCase`; подмена требует изменения кода потребителя.

## Решение

Принят вариант 2. Контракт `WarehouseApi` вынесен в `core/contracts/WarehouseApi.kt`. Потребитель `MakeDishViewModel` принимает `WarehouseApi` в конструкторе и вызывает `consumeIngredients`. Реализация выбирается в точке сборки (`WarehouseDependencies` для рабочей версии, `FakeWarehouseApi` для проверки потребителя).

## Последствия

Что решение дает:
- потребитель можно тестировать без базы и эмулятора (`FakeWarehouseApi`);
- подмена подтверждена: `MakeDishViewModelFactory` принимает любую реализацию `WarehouseApi`, код `MakeDishViewModel` не изменяется;
- контракт документирован в KDoc по стандарту стека (Kotlin).

Чем за это платим:
- цена решения — дополнительный интерфейс `WarehouseApi` и класс `FakeWarehouseApi`;
- при изменении контракта нужно обновлять обе реализации;
- `FakeWarehouseApi` не подтверждает работу базы Room и распределение по партиям — это проверяется только через `WarehouseApiImpl`.

## Способ проверки

Запуск `MakeDishViewModel` с `WarehouseApiImpl` (через приложение на эмуляторе) и с `FakeWarehouseApi` (через модульные тесты JVM). Код потребителя при этом не изменяется. Результаты проверок зафиксированы в ПЗ №2.
