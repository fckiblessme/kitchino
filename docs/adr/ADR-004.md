## Контекст

Модуль склада строит прогноз расхода продуктов. `IngredientsViewModel` пересчитывает прогноз по всему каталогу ингредиентов, вызывая `ForecastUseCase.execute` последовательно для каждого ингредиента. Внутри `ForecastUseCase` история списаний читается через `WarehouseRepository` дважды: запрос `getDailyConsumptionSince` возвращает суммы по дням окна наблюдения 30 дней, а запрос `getDailyConsumption` повторно читает всю историю ингредиента только для того, чтобы определить день первого списания.

До этой работы модель исполнения участка была выбрана по предположению, а не по измерению. Требовалось определить, какая модель исполнения подходит модулю, и какова цена повторного чтения истории.

## Гипотезы и результаты измерений

Каждая гипотеза сформулирована и ее ожидаемое значение записано до измерения. Измерения выполнены по единому протоколу: прогрев, серия из пяти повторов, медиана и относительный размах.

| Гипотеза | Ожидание до измерения | Результат | Протокол |
|---|---|---|---|
| Чистая арифметика без обращения к памяти масштабируется по числу исполнителей | ускорение близко к числу исполнителей | ускорение 1,88 при p = 2, 3,66 при p = 4, 6,81 при p = 12; эффективность 94, 92, 57 процентов | `docs/experiments/pz04-warehouse-sanity.txt` |
| Пересчет прогноза по каталогу ускоряется при параллельном исполнении | ускорение растет с числом исполнителей | ускорение 1,08 при p = 2, 0,97 при p = 4, 0,85 при p = 12: выигрыша нет | `docs/experiments/pz04-warehouse-cpu.txt` |
| Время построения прогноза линейно зависит от числа записей журнала | при росте записей в 10 раз время растет в 10 раз | отношение времени 9,94 | `docs/experiments/pz04-warehouse-mechanism.txt` |
| Синхронное чтение записей уступает асинхронному | ускорение близко к числу записей | ускорение 9,78 при 10 записях | `docs/experiments/pz04-warehouse-io.txt` |
| Общий изменяемый итог без синхронизации теряет обновления | итог меньше ожидаемого | итог без синхронизации меньше ожидаемого, с блокировкой и локальными счетчиками точный | `docs/experiments/pz04-warehouse-state.txt` |
| Повторное чтение истории удваивает стоимость проходов | отношение около 2, экономия около половины | отношение 1,79, экономия 44,2 процента | `docs/experiments/pz04-warehouse-alternative.txt` |

Сопоставление двух первых измерений дает механизм: среда исполнения параллельна, но пересчет прогноза упирается в пропускную способность памяти при чтении журналов, поэтому добавление исполнителей не увеличивает скорость.

## Решение

1. Пересчет прогноза по каталогу ингредиентов выполняется последовательно. Параллельное исполнение не внедряется: измеренное ускорение не превышает единицы, а при большом числе исполнителей появляется проигрыш из-за накладных расходов.
2. Операции чтения из базы выполняются асинхронно: время ожидания ответа не суммируется, ускорение близко к числу одновременных операций.
3. Сводные итоги по складу изменяются через локальные счетчики исполнителей с однократным слиянием. Общая блокировка применяется только там, где работу нельзя разделить на независимые части.
4. Повторное чтение истории устраняется: день первого списания запрашивается одним агрегатным значением вместо повторной выборки всей истории ингредиента.

## Рассмотренные альтернативы

- Параллельный пересчет прогноза по ингредиентам отвергнут: измеренное ускорение 1,08, 0,97 и 0,85 при двух, четырех и двенадцати исполнителях. Стоимость в виде накладных расходов превышает выигрыш.
- Защита общего итога блокировкой принята как резервный вариант: она корректна, но в 31,41 раза медленнее локальных счетчиков на том же объеме работы. Гонка без синхронизации воспроизведена в 20 запусках из 20.
- Сохранение повторного чтения истории отвергнуто: второй проход забирает 44,2 процента времени построения прогноза при полностью совпадающем результате.

## Последствия

- Модуль остается предсказуемым по времени: стоимость прогноза линейна по глубине истории и ограничена окном наблюдения 30 дней.
- Отказ от параллельного пересчета снижает сложность кода и исключает гонки в общем состоянии.
- Устранение повторного чтения сокращает время построения прогноза почти вдвое на больших журналах, изменений в результатах прогноза нет.
- Для операций ввода-вывода требуется асинхронная форма вызова; синхронные вызовы в цикле недопустимы.

## Условие пересмотра

Решение пересматривается при изменении профиля нагрузки: если каталог вырастет настолько, что пересчет прогноза перестанет укладываться в допустимое время отклика интерфейса, или если окно наблюдения будет увеличено и объем истории на ингредиент вырастет на порядок. В этом случае гипотезу о параллельном исполнении проверяют повторно по тому же протоколу, и решение принимается по новым измерениям.
